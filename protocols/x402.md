## What It Is

Settlement layer for per-request agent payments using HTTP 402 status code. An agent hits an API, gets a 402 response, signs a payment authorization, attaches it to the retry, and the payment settles on-chain. On EVM the `exact` scheme uses EIP-3009 `transferWithAuthorization` by default, with Permit2 as the alternative transfer method (EIP-2612 approvals via a gas-sponsoring extension). No accounts, no API keys, no invoices.

## Core Concepts

- **402 Response** — server returns payment requirements (amount, recipient, chain)
- **Facilitator** — verifies the payment permit and settles on-chain. Coinbase runs one, but anyone can run their own.
- **Schemes** — `exact`, `upto` (EVM: TS/Go/Python; SVM: TS/Go), `batch-settlement` (EVM: all three SDKs; SVM: TS/Go), and `auth-capture` (two-phase hold/capture, EVM: TypeScript and Go)
- **Spend controls (SDK-level, all three SDKs)** — on by default: the client only pays in assets it recognizes, with a `$1` USD ceiling per payment (`maxAmountPerPayment`), checked before the payload is signed. Other assets are opt-in via `allowedAssets`; `spendControls: false` (TypeScript) or `DisableSpendControls()` (Go) turns them off. Per-payment guardrail, not a running budget across payments.
- **Multi-chain** — `exact` scheme specs for EVM chains (Base, Ethereum, Polygon and others), Solana, Algorand, Aptos, Canton, Cardano, Casper, Concordium, Hedera, Keeta, Lightning (BTC), NEAR, Starknet, Stellar, Sui, TON and XRPL. SDK coverage is narrower: TypeScript covers the most; Go covers EVM and Solana, Python EVM, Solana and TON.
- **Upto scheme** — variable/max pricing (authorize up to X, settle actual usage). Shipped in TypeScript and Go (EVM + SVM) and Python (EVM). Spec covers both EVM (`scheme_upto_evm.md`) and SVM/Solana (`scheme_upto_svm.md`). On SVM the voucher signer is optionally delegated: a facilitator advertises `receiverAuthorizer` in `/supported`, and a resource server that ships no signer of its own lets the facilitator sign.

## What It Covers

- Per-request micropayments (agent pays per API call)
- On-chain settlement with gasless signing (EIP-3009 or Permit2 on EVM)
- Facilitator architecture (verification + settlement)
- MCP transport (payment signaling in MCP tool calls)
- A2A transport
- Multi-chain support across EVM and non-EVM
- Optional signed receipts (Offer and Receipt extension): the resource server signs a receipt naming the payer, resource, network and time. The transaction hash is optional and omitted by default for privacy. It records what the merchant says happened, not what the agent was authorized to do, and it is signed by the merchant's key.

## What It Doesn't Cover

- Client-side budget management — **explicitly out of scope** in `specs/x402-specification-v2.md` on main, even though all three SDKs ship per-payment spend controls
- Agent delegation or mandates — not defined in the spec (the spec is silent; it is not on the out-of-scope list)
- Cross-service spending coordination — not defined
- Subscription/recurring payments — not defined as a scheme; the spec mentions subscription models only as use cases

The spec's `asset` field accepts an ISO 4217 currency code for fiat, so fiat is not excluded by the protocol, though every scheme spec today settles on a blockchain or Lightning.

## Relationship to Other Protocols

- **Competes with MPP** at the settlement layer (crypto rails vs multi-rail)
- **Plugs into AP2** via the A2A x402 extension (crypto settlement for AP2 mandated purchases)
- **Independent of ACP/UCP** at the commerce layer

## Recent Changes (since 2026-06-01)

- **`spendControls` in the TypeScript client** ([PR #3124](https://github.com/x402-foundation/x402/pull/3124), merged 2026-08-13; docs [PR #3147](https://github.com/x402-foundation/x402/pull/3147), merged 2026-08-13) — per-payment USD cap (default `"$1"`) plus an asset allowlist, enforced before signing. TypeScript only at first; Python and Go followed on 2026-08-18 (below).
- **`upto` scheme on Solana** — SVM payment flow in the TS SDK ([PR #3094](https://github.com/x402-foundation/x402/pull/3094), merged 2026-08-12), spec `scheme_upto_svm.md` ([PR #3135](https://github.com/x402-foundation/x402/pull/3135), merged 2026-08-12), ComputeBudget instructions added ([PR #3155](https://github.com/x402-foundation/x402/pull/3155), merged 2026-08-14). `upto` was EVM-only before this.
- **Delegated receiver authorizer for SVM `upto`** ([PR #3346](https://github.com/x402-foundation/x402/pull/3346) TypeScript, [PR #3347](https://github.com/x402-foundation/x402/pull/3347) Go, both merged 2026-09-03; Go facilitator config documented in [PR #3356](https://github.com/x402-foundation/x402/pull/3356)) — the facilitator may advertise `receiverAuthorizer` in `/supported`; a resource server that omits its own signer delegates voucher signing, and the facilitator signs after correlating the claim settle to the same authenticated caller that opened the channel. This changed the spec (`specs/schemes/upto/scheme_upto_svm.md`), not only the SDKs.
- **Spend controls in Python and Go** ([PR #3154](https://github.com/x402-foundation/x402/pull/3154) Python, [PR #3156](https://github.com/x402-foundation/x402/pull/3156) Go, both merged 2026-08-18) — the TypeScript feature now exists in all three SDKs.
- **`auth-capture` in Go** ([PR #3622](https://github.com/x402-foundation/x402/pull/3622), merged 2026-10-05) — EVM auth-capture for the Go server and facilitator SDKs. TypeScript auth-capture SDK v1.1 ([PR #3203](https://github.com/x402-foundation/x402/pull/3203), merged 2026-10-06; docs [PR #3708](https://github.com/x402-foundation/x402/pull/3708)).
- **SDK versions** — TypeScript 2.28.0 (npm), Go v2.28.0 (Go module proxy, 2026-09-29), Python 2.25.0 (PyPI)
